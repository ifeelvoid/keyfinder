# Free offline key-detection references on Apple Silicon

Research and local inspection: 2026-10-11. Owner: libraries research chat for brief #0003.

## Outcome

**First runnable reference: librosa CQT chroma plus a fixed, explicitly named Krumhansl–Schmuckler scoring implementation. Second experiment: Essentia `KeyExtractor` with `profileType="bgate"`, keeping all parameters and package versions fixed.** Retain standalone libkeyfinder as an additional established baseline once its existing CLI wrapper is located or recreated by the implementation owner. Defer madmom until after these comparisons: it provides a published neural reference, but its old release/runtime and separate model license add friction.

This is a practical sequencing recommendation, not a ranking of measured accuracy. Librosa's feature extractor runs here today; it has no built-in song-key classifier. Essentia provides an actual integrated key detector. Neither agreement nor a synthetic smoke test establishes accuracy on Alexander's music. The anchor constraint is independent, reviewed labels for exact recordings with a song-family split that excludes training/tuning material.

No library was installed by this research chat. The coordinating chat installed the isolated librosa environment during this investigation and owns real-song execution. This chat inspected dependencies and ran only an in-memory synthetic feature smoke check. Only this report was written in the implementation checkout; detector code and the primary dirty CNN checkout were left untouched.

## Evidence levels

- **Confirmed from current local artifacts:** files, architecture, interpreter launch failures, dependency metadata, synthetic feature result, dynamic-library load, and the isolated CNN evaluator-function result listed below.
- **Confirmed from primary sources:** documented APIs, published wheels, source/model licenses and historical paper results, with links beside the relevant claims.
- **Reasonable inference:** the proposed reference order reduces immediate runtime friction and separates feature-extraction effects from changes in scoring.
- **Missing or needs verification:** real-song accuracy, full decoder coverage, Essentia import/inference on this host, madmom compilation/inference, checkpoint provenance, trained-versus-random status, and model/test overlap.

### API and compatibility details that matter

- Librosa is an analysis toolkit, not a pretrained key detector. `key_to_notes` and related notation utilities accept a known key; they do not estimate one. The reference adapter must own profile constants, aggregation, tuning, candidate ordering, handling of silence/nonfinite inputs, and its scoring formula. Keep those settings fixed before running the held-out evaluation.
- Installed librosa 1.0.0 metadata requires Python >=3.12, NumPy >=2.1 and Numba >=0.61. This is a different dependency generation from the old CNN's Python 3.9 environment. Do not repair that old environment by pointing it at the new benchmark venv. Both `load` and `loadx` are available locally; use `load` with explicit local file paths. `loadx` is for example audio and is unnecessary here.
- Essentia's current default profile is `bgate`, not a universal historical “Essentia baseline.” Profile choice materially changes the algorithm. At HPCP size 12, posterior detuning correction cannot use sub-semitone resolution; size 36 deliberately makes this available. Record the choice rather than changing it silently between runs. `strength` is a profile-fit output, not a calibrated probability. [Extractor parameters](https://essentia.upf.edu/reference/std_KeyExtractor.html), [Key/profile definitions](https://essentia.upf.edu/reference/std_Key.html).
- Essentia's old installation page still shows `/usr/local` Homebrew paths; this Mac uses `/opt/homebrew`. Wheel tags are stronger evidence of current arm64 availability than that old path example. TensorFlow support is unnecessary for this experiment; upstream has an open Apple Silicon TensorFlow-module issue, which should not be generalized into a failure of non-TensorFlow `KeyExtractor`. [Upstream issue 1486](https://github.com/MTG/essentia/issues/1486).
- Madmom's 0.16.1 release predates current Python/NumPy versions. An upstream issue documents the Python 3.10 `MutableSequence` import break; current development source has changed that import to `collections.abc`. This is evidence of version drift, not proof that current development source fully supports Python 3.12/NumPy 2.5.4. Pin a source revision if investigating it, include its models/submodule, and test native import plus actual inference. [Issue 502](https://github.com/CPJKU/madmom/issues/502), [current processor source](https://raw.githubusercontent.com/CPJKU/madmom/main/madmom/processors.py).
- Madmom's classes start with A major through Ab major, then A minor through G# minor. They are neither C-first chroma indices nor the old CNN's Camelot-first indices. Preserve canonical tonic/mode conversion explicitly. Its pipeline uses mono 44.1 kHz audio, 8192-sample frames at 5 fps and 24 log-frequency bands/octave over 65–2100 Hz. [Implementation](https://raw.githubusercontent.com/CPJKU/madmom/main/madmom/features/key.py).
- Local benchmarking and app redistribution are different decisions. Essentia's site describes its AGPL option as noncommercial, while the published source/wheel license is AGPL; do not describe the code itself as a CC noncommercial model license. Review the exact component/dependency terms before bundling anything into the MIT app. An external benchmark adapter does not automatically settle every distribution obligation. [License text](https://raw.githubusercontent.com/MTG/essentia/master/COPYING.txt), [upstream explanation](https://essentia.upf.edu/licensing_information.html).

## Credible published evaluation and its limits

1. **Essentia profile methods and the original KeyFinder:** Faraldo, Jordà and Herrera, *A Multi-Profile Method for Key Estimation in EDM* (peer-reviewed AES Semantic Audio, 2017), Table 2 compares bgate, original KeyFinder and Mixed In Key 7. On GiantSteps it reports exact/weighted scores of 64.1%/72.5% for bgate, 60.4%/69.9% for KeyFinder and 67.2%/74.2% for MIK. These are historical implementations and recordings, not tests of our Swift app or a guarantee for current wheels. The paper distinguishes the older Essentia baseline from tuned EDM profiles; the library name alone is not a reproducible configuration. [Paper](https://mtg.upf.edu/system/files/publications/aes_FARALDO_cameraReady.pdf).
2. **Madmom's documented neural method:** Korzeniowski and Widmer, *Genre-Agnostic Key Classification With Convolutional Neural Networks* (ISMIR 2018), Table 2 reports AllConv GiantSteps 67.9% exact / 74.6% weighted and the independent KeyFinder collection 70.0% exact / 76.1% weighted. These support the method as a credible comparator, not the accuracy of every bundled model or this checkpoint. The work trains on GiantSteps-MTG, Billboard and classical data; overlap must be checked before using those collections as independent tests of pretrained models. [Paper](https://ismir2018.ircam.fr/doc/pdfs/7_Paper.pdf).
3. **Librosa:** the primary chroma documentation describes feature extraction; it provides no accuracy figure for a built-in global-key classifier because that is not the feature API's task. Do not attach a neural paper's score to a custom CQT+KS baseline. Measure the explicitly named adapter on reviewed recordings. [Chroma tutorial](https://librosa.org/doc/1.0.0/auto_tutorials/03-advanced/plot_chroma.html).
4. **Original libkeyfinder context:** the original author's project report explains its chroma/profile algorithm and author-run evaluations. It is useful for design provenance, but not a fresh performance measurement of 2.2.8 or Alexander's detector. Use the peer-reviewed comparison above as historical corroboration. [Author's project report](https://www.ibrahimshaath.co.uk/keyfinder/KeyFinder.pdf).

Always publish exact tonic+mode accuracy separately from weighted MIREX-style score. For modern scoring, explicitly enable descending fifths if using `mir_eval.key.weighted_score`: its documented default is `allow_descending_fifths=False`, while `True` matches MIREX since 2017. A related-key score is not an exact-key success. [Evaluator documentation](https://mir-eval.readthedocs.io/latest/api/key.html).

## Existing dirty CNN work: what actually exists

Read-only source checkout: `/Volumes/X6 SSD/Code/Apps/keyfinder`. Its dirty Swift files, app bundle and untracked `cnn-backend` were preserved.

**Present:** `model.py` defines a PyTorch AllConv-like `KeyNet`; `dataset.py` defines Camelot labels and random pitch-shift/snippet access; `preprocess_data.py`, `train.py`, `eval.py`, `predict_keys.py`, `compare_algorithms.py` and `cnn_bridge.py` provide a pipeline; `CNNBridge.swift` launches the Python JSON bridge. `AudioAnalysisModel.swift` has CNN override/fallback paths and sets `useCNN=false` by default. `build-app.sh` copies the backend, including its environment, into app resources.

**A real checkpoint file is present:** `cnn-backend/checkpoints/keynet.pt`, 1,874,533 bytes, SHA-256 `fc92072f1b9b19552ce3b74a9c8ce0cecb97633a12ae524ac0d93c05800e354e`. ZIP inspection without unpickling finds an `allconv_keynet` archive and 54 tensor-storage entries. This proves a checkpoint artifact exists; it does not prove successful local training, nonrandom weights, fit to this architecture or validation quality. Torch/model inference was not run.

**Runtime currently fails before inference:** both source and bundled `venv/bin/python3` symlink to `/Applications/Xcode.app/Contents/Developer/usr/bin/python3`, which is absent here. Launching each returns `FileNotFoundError`. Both venv folders exist, but are not portable working runtimes. System/Homebrew Python inspection found none of Essentia, librosa, madmom, NumPy, SciPy, Torch or Torchaudio. The new isolated benchmark venv is separate and contains no Torch/Torchaudio.

**Integration has another unresolved path issue:** `CNNBridge.swift` passes the script and audio path, without setting a subprocess working directory or an absolute `--model_path`. `cnn_bridge.py` defaults to relative `checkpoints/keynet.pt`. Even after repairing Python, checkpoint lookup depends on the launch directory. The bridge uses CPU by default; the training script selects CUDA or CPU and contains no MPS selection. These are static findings, not tested app failures beyond the observed missing interpreter.

**Not a reproduced published neural method:** this backend uses librosa CQT; upstream madmom uses a log-filtered STFT. Its own preprocessing comments acknowledge that difference. Existing architecture/code can be reused as a future experiment, but substituting official madmom weights into this PyTorch/CQT model is not justified.

**Validation evidence is incomplete and inconsistent:** no `Dataset`, `logs` or `training_logs` directories were found in this backend. The README reports 66.72% exact / 73.51% weighted for `keynet.pt`, but no local fingerprinted run reproduces that result. Its README table names Mixed In Key 8.3, while `evaluation/README.md` and `mixedinkey_10.3.txt` name version 10.3. Vendor output text files are comparison predictions, not human ground truth or provenance for our checkpoint. `BENCHMARK.md` is a three-track KS/genre-preset report, not a validation of this CNN.

**Evaluator bug confirmed without importing Torch:** extracted only `mirex_category` from `eval.py` via Python AST and tested all 12 same-tonic opposite-mode pairs using the local mapping. It labels C#/F#/B parallel-mode pairs as `rest`, while the other nine are `parallel`, because it checks absolute Camelot-index difference `-15` and misses the wrapped `-3` cases. Do not reuse this evaluator as the canonical benchmark implementation or trust scores until corrected and rerun by its owner. No source was edited.

The backend source has an MIT license attributed to Alexander Sommer (2025). There is no separately observed checkpoint model card, training manifest or weight-license statement here. Do not infer weight provenance or redistribution rights from the copied source license alone.
